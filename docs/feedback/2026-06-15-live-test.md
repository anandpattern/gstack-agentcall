# GStack joins-meeting — feedback from live test (2026-06-15)

Captured during a real founding-team dispatch (office-hours / CEO / Eng Manager)
into a Google Meet, with Claude acting as the brain. Ordered by severity.

## Critical

1. **Recall does not evict orphaned cloud bots.**
   When the local bridge dies (e.g. a network drop), the AgentCall *cloud*
   session stays in the meeting. `/recall {all:true}` and killing local
   processes did **not** remove the bots — they sat visibly in the room.
   The only thing that worked was calling the AgentCall API directly and
   sending `{"type":"meeting.leave"}` per `call_id`.
   → Recall should reconcile against live AgentCall calls, not just
   locally-tracked PIDs.

2. **State desync between local tracking and reality.**
   `active.json` showed `runners: []` while three bots were still live in
   the meeting (confirmed via `GET /v1/calls/{id}` → `status: bot_ready`).
   Local state must reflect actual AgentCall call status, or a reconcile
   step must run on recall/startup.

3. **Broker connection flaps on a marginal network.**
   The worker WS dropped every ~1–2 min with `1011 keepalive ping timeout`,
   and reconnects intermittently failed DNS. Every reconnect produced a
   **new `worker_id`**, so the broker saw a brand-new worker each cycle and
   orphaned the previous one.
   → Persist a stable worker identity across reconnects; loosen keepalive
   timeouts; collapse the reconnect churn.

4. **Idle/abandoned dispatches keep billing.**
   Bots dispatched but never admitted from the lobby sat idle ~48 minutes
   (billing AgentCall the whole time) before being cleaned up.
   → Auto-recall if not admitted within N minutes, or if no human is ever
   present.

## Medium

5. **Unretrieved task exceptions.** On every disconnect the worker logs
   `Task exception was never retrieved` (the `reader()` task's exception is
   never awaited). Noisy; should be caught/handled.

6. **Avatar join is slow + manual.** ~30s to appear, and each bot must be
   admitted from the lobby manually — very easy to forget and orphan them
   (this is what caused #4).

7. **Heavy talk-over.** Constant `tts.interrupted: reason=user_speaking`.
   Consider barge-in handling and a shorter default reply length so the
   bot's turn lands in the speaker's pauses.

## Nice to have

8. **One "hard reset / leave everything" command** that reconciles BOTH
   local state and live AgentCall calls and guarantees the room is empty.

9. **STT quality** garbled most utterances ("subscription" → "procession
   building", names mangled). Lower-confidence transcripts could be flagged
   so the brain can ask for a repeat instead of guessing.

---

## Reported live by Anand (in-call)

A. **Bots all talk at once at call start.** In multi-agent mode, when the
   call begins every specialist starts speaking simultaneously and they
   interrupt each other. Turn-taking must be enforced from the very first
   greeting — only one speaks at a time. (The cross-bot speech lock exists
   for mid-call turns but the initial auto-greetings appear to bypass it.)

B. **Specialists should drive the conversation, not just react.** Since the
   bot now joins "like a real person," it should be proactive: after taking
   the user's input it should ask follow-up questions, draft the output
   (notes/spec/doc), and share it back — leading the session rather than
   waiting to be prompted each turn. This is also the moment to actively
   show off the AgentCall capability, not sit passively.

C. **Use richer output modalities to reach a wider audience.** Beyond voice,
   the bot should: screenshare when it helps, post details/links/research in
   meeting chat, and even screenshare a prototype or a localhost port of
   something it built. Lean on the full capability set (screenshare URL/port,
   send_chat), not voice alone.

D. **Bot's own voice is transcribed back as user input (echo loop).** A
   specialist's spoken TTS reply reappeared in `inbox.jsonl` as a
   `user.message` attributed to the human speaker. This pollutes the
   transcript and risks the brain responding to its own output. Needs echo
   suppression / self-audio tagging in STT, or dedupe of recently-spoken
   bot text from inbound transcripts.

E. **Destination:** Anand wants this list fed into the cloud session / repo
   where the GStack meeting platform is built, so it can be tracked and
   updated there.

F. **Dashboard has no working recall/remove control.** Specialists deployed
   from the platform/dashboard can't be recalled or removed from the meeting
   through the UI. Confirmed live today — when the local bridge died, neither
   the dashboard nor `/recall` could evict them and the bots were stuck in
   the room (ties to #1/#2). The dashboard needs a recall/remove-specialist
   button that actually reconciles and ENDS the live AgentCall calls.

G. **Recall ends the call but does not reap local processes.** A clean
   `/recall {all:true}` correctly ended the AgentCall calls (`status: ended`)
   and cleared `active.json`, but the `specialist_runner.py`, `launch-visual.sh`,
   and `tail -f *.cmds` processes stayed alive afterward and had to be killed
   manually. These lingering trees are exactly what become orphans after a
   network blip — recall should terminate the full process tree, not just end
   the call and clear state.
